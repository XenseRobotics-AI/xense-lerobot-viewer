# 质检诊断记录与保存稳定性实施计划

日期：2026-11-03。范围：质检计时、请求关联、服务端保存诊断与性能边界。

## 目标与边界

- 能区分客户端未提供快照、计时未就绪、采集异常、请求失败和存储失败；历史记录缺失保持未知。
- 内容时长、覆盖率、已保存停留快照口径保持独立，日期统一使用项目 UTC+8 零点标准。
- 只记录关键状态与耗时，不逐帧采集，不把诊断事件写入业务质检 JSON，不记录完整请求、凭证或视频内容。
- 日志故障不能阻止业务保存；有界队列、批量追加、文件轮转与保留上限控制成本。
- 保留当前工作区及 main 的已有提交，只同步本任务及其必要依赖；不修改真实数据集记录。

## 顺序与验收

1. 协议与版本关联：定义有界诊断结构、客户端/服务端版本、会话/操作/请求 ID 与快照状态；旧请求继续可用，未知值不伪造原因。
2. 客户端采集：在现有计时 hook 维护计时启停/就绪/存储异常摘要，随保存请求提交；不增加独立的高频网络请求。
3. 服务端日志：记录接收、校验、锁等待、读取、临时文件写入、提交与响应阶段；日志脱离业务文件，错误消息及标识需清洗限长。
4. 保存稳定性：增加显式请求超时；超时不等于未提交，核对服务端状态后再决定结果；不盲目重放可能覆盖更新操作的写请求。
5. 故障与性能测试：覆盖旧客户端、缺快照、正常零值、采集异常、并发保存、日志不可写/队列饱和/轮转、超时后已提交与未提交、后续队列继续；对比启用前后的负载与延迟。
6. 集成与交付：运行类型、lint、格式及全量测试，在独立 worktree 合入最新 origin/main，保留 main 既有提交，验证后提交并推送 main；将相关代码同步回当前功能工作区。

## 风险与控制

- 超时后服务端仍可能提交：保存结果先做读回确认；不能确认时明确显示结果未知并继续允许核对，禁止显示成功。
- 全文件 JSON 写入随记录数增长：本次不更换业务存储，仅增加阶段耗时，日志独立存储以免进一步放大重写成本。
- 共享盘锁与多进程：保留现有锁协议；诊断文件按进程区分并限制保留，不让多个进程争用同一日志轮转锁。
- 浏览器时间不能证明服务端耗时：客户端用单调时钟记录相对耗时，服务端独立计时；标记日期仍由服务端产生。
- 详细日志采用尽力记录，不能替代持久审计或备份；队列丢弃/写失败必须有可观测计数。
