# 视频播放优化复查

本文的实机测量来自本地 fork main。面向上游 main 的 PR 只移植播放器相关改动；
上游旧版的播放时钟被拆出并补入暂停/长任务修正，Canvas 的绘制频率、模型、
阴影和分辨率设置没有改动。工作台改动没有包含在该 PR 中。

日期：2026-11-19。范围：八路回放的解码、同步与视频组件重绘。

## 已落实的优化

`FirstFrameVideo` 使用 React memo；普通视频页面和 3D Replay 均通过稳定的时间 ref 传入最新时钟。
正常播放时不再重绘视频显示组件，同步逻辑仍按原策略运行。视频源、Episode、
显示状态或语言变化仍可触发更新；切换源时在 layout effect 内读取最新目标时间。

两个播放器的浏览器回归均补充了暂停时切换 Episode 和视频源：同一 MP4 的 Episode 切换不重载，
新源每路只加载一次，两种操作均须到达新的目标帧。

压测服务器延长连接空闲时限，并保留每个 Range 响应的独立字节副本。
真实大视频的状态等待上限为 30 秒，小夹具保持 6 秒；超时输出各路媒体状态和错误。

## 实测结果

使用无界面 Chromium、关闭 GPU、React 开发模式；以下是测试环境结果。
在组件入口临时计数，每种配置连续采样三次，每次 5 秒；计数代码未加入产品。

| 八路低分辨率夹具            | 优化前     | 优化后     |
| --------------------------- | ---------- | ---------- |
| 视频显示组件渲染次数 / 5 秒 | 1200–2400  | 0          |
| JavaScript 耗时 / 5 秒      | 221–328 ms | 193–453 ms |
| 新增 seek、媒体重载、掉帧   | 均为 0     | 均为 0     |

开发模式包含 Strict Mode 的重复调用。渲染次数显著减少，但耗时有波动，
这组结果不能证明总 CPU 占用或端到端播放速度按固定比例改善。

高分辨率合成夹具包含两路 1920×1080 腕部、两路 1280×960 头部、
四路 700×400 触觉视频，均为 H.264、30 fps。正常 CPU 配置下：

- 八路全部就绪耗时约 15.7 秒，原约 6 秒的就绪断言会误报失败。
- 前两个 5 秒窗口仍有启动期恢复：合计 62 帧掉帧、2 次漂移修正，无重载或错误。
- 第三个 5 秒窗口各路约 150 帧，均无掉帧、seek、重载或错误；
  最大时间偏差约 52 ms，视频显示组件渲染次数为 0。

在优化前的极限压测中，四倍 CPU 降速叠加三次 650 ms 主线程阻塞会产生
4 次同步 seek，视频画面保持可见、无重载或错误。这不满足压测脚本的零 seek
断言，说明这组高分辨率负载需要单独评估，不能用低分辨率回归代替。

优化后的极限复测中，保留独立 Range 响应副本时八路均就绪，阻塞阶段仍有
1 次同步 seek，严格的零 seek 压测仍未通过。另一次尝试共享响应字节视图时，
两路出现媒体格式错误；单次对照不足以确定原因，因此没有保留这项测试服务器改动。

41 项相关单测、1000 次播放/暂停浏览器回归、类型和格式检查通过。
lint 通过，保留项目其他组件原有的两项 Hook 依赖警告。

## 明显卡顿的追加检查

用户要求保留原有 3D 实现和画质。此前尝试降低渲染分辨率、关闭阴影、简化
CAD 网格的改动已全部撤回，相关模型加载、依赖文件也已恢复。保留的代码改动
仅减少普通视频页面和回放视频浮层的 React 重绘；没有保留任何 3D 降质方案。

普通页面八路低分辨率夹具在三个 5 秒窗口中的 `FirstFrameVideo` 渲染次数
均从 304 次降至 0 次，各路仍解码 150–151 帧，无掉帧、seek、重载或错误。
这是减少 React 开销的验证，不能证明用户报告的明显卡顿已解决。

真实样本为 `xtac-umi-g1-vt061-261117` 的 Episode 0：两路 1024×768 头部、
两路 640×480 腕部、四路 700×400 触觉视频。普通页面两个 6 秒窗口中，
各路解码 180–181 帧，无媒体等待、掉帧、seek 或重载；视频帧回调最大间隔
约 67 ms，未复现持续卡顿。

恢复原画质后，3D 页面两个 6 秒窗口仅收到约 31–32 次视频帧回调，最大间隔
约 267–417 ms，而各路仍解码约 185–206 帧；每个窗口约有 32–33 次主线程
长任务，没有额外 seek 或重载。测试浏览器的 WebGL 渲染器经读取确认为
**SwiftShader 软件渲染**：测试启动参数关闭了 GPU。因而这里的绘制瓶颈不能
直接代表用户浏览器，也不能作为降低原有画质的依据。解码帧数和零 seek
同样不能替代实际画面呈现流畅度的验证。

追加改动的 40 项相关单测、1000 次播放/暂停和两个播放器的 Episode/视频源
切换回归均通过；类型、lint、格式检查通过，lint 仍有两项原有依赖警告。

## 首帧启动优化

本轮目标是在 Intel 集显下改善八路首帧启动，保留视频编码、时间戳、原始文件
和 3D 实现。样本仍为 `xtac-umi-g1-test-261116` Episode 0。

八路原始 MP4 均为 `ftyp / mdat / moov`，索引位于尾部。播放器现在通过独立的
`?playback=1` 响应读取 `ftyp / moov / mdat`；服务端只读取小段头部和索引，修正
`stco`、`co64` 偏移，按 Range 流式映射原有媒体字节。没有转码、临时整文件副本
或数据集写入；原下载 URL 仍返回原始字节。不支持的布局、碎片化 MP4、索引
超过 4 MB 或偏移不能安全转换时，使用原始文件。临时 I/O 失败不会缓存为另一
种字节布局，避免后续 Range 混用不同偏移。

索引缓存上限为 64 项、16 MB，按文件大小和修改时间失效，同版本并发请求共享
一次检查。媒体和索引输出均以至多 64 KB 的块流式读取，支持请求中止和 reader
取消；首个开放 Range 缩小为 256 KB，后续仍为 2 MB。较大的索引可增大首段，
显式 Range 和后缀 Range 保持原语义。

初始零时刻的 `loadeddata` 可直接解除遮罩，省去额外两帧 RAF 等待；非零片段、
显式跳转和切换 Episode 仍验证目标帧。提示先显示“正在读取视频”，索引就绪后
显示“正在解码画面”，避免从请求开始就把全部等待称为解码。

最终生产模式对照使用同一 Windows Chrome、1600×950 视口和 Intel UHD / D3D11。
用 CDP 请求拦截将基线请求改为原始字节，保持相同页面代码；每次导航清空浏览器
HTTP 缓存，不清空 NAS 或 OS 缓存。指标从首个 `loadstart` 到八路遮罩全部解除。
最终采样没有同时运行压力测试或构建。

| 页面与采样              | 原始响应视频启动 | 优化响应视频启动 |
| ----------------------- | ---------------- | ---------------- |
| 3D Replay 首对采样      | 927 ms           | 1193 ms          |
| 3D Replay 热运行第 1 对 | 958 ms           | 797 ms           |
| 3D Replay 热运行第 2 对 | 917 ms           | 748 ms           |
| Episodes 单对采样       | 298 ms           | 259 ms           |

热运行的 3D 视频启动约减少 18%；这是少量本机采样，不承诺固定降幅。首对采样的
视频阶段较慢，整页时间及前置加载仍有波动，不能把热运行收益当作所有冷启动的
保证。优化消除了尾部索引请求，但因首段较小，后台顺序缓冲的请求总数可能增加。

八路逐一执行 `ffprobe -show_packets -show_data_hash sha256`，每路 1600 个编码
数据包的哈希、PTS、DTS、时长和大小全部与原文件一致。新测试覆盖跨索引/媒体
边界的 Range、原始下载、文件替换后的缓存失效、64 位大分片、32 位溢出、异常
索引回退和取消后文件描述符关闭。播放回归已改为使用实际文件 API 和尾部索引
H.264，覆盖 1000 次播放/暂停；真实八路阻塞恢复、同步修正和循环检查通过。
最终 `bun run validate` 通过类型、lint、格式和 1581 项测试。

最终生产页面再次采样两个 5 秒播放窗口，八路每个窗口均呈现约 150 帧，掉帧、
等待、seek、重载和脚本错误均为零；截图确认八路首帧全部显示。本轮独立新浏览器
整页启动约 3.9 秒，再次说明热运行的视频阶段计时不能等同于全部冷启动耗时。

3000 开发页面自动使用本轮实现；3001 生产预览已重建，构建标识为

## 高清 HEVC 与 3D 同时播放的卡顿复查

用户反馈 3000 开发页面仍明显卡顿。本轮补测真实窗口和试管数据集
`/mnt/datasets/after-261024-lerobot/xtac-umi-g1-clean-test-tube-turn-upside-down-261118`
Episode 0。该数据实际为 HEVC/H.265：腕部 1920×1080，头部 1280×960，触觉
700×400，均为 30 fps，与此前的较小 H.264 样本不同。测试使用 Windows Chrome、
Intel UHD / D3D11 和 1920×1080 视口，并排除测试窗口被遮挡时的后台节流。

同一数据在普通视频页两轮各 8 秒均呈现约 240 帧，零掉帧、等待、seek。3D 页则
出现数秒帧回调间隔，反复同步 seek，缓冲仍充足；生产版也复现。临时屏蔽同步
seek 仍不能恢复流畅，说明它不是唯一原因。禁用硬件解码时 Chrome 不支持该
HEVC 软件路径；无损 H.264 测试副本使解码改善，却引入大码率缓冲问题，因此

## 保持原 3D 绘制频率的无损兼容播放

新增可选“流畅播放（原画质）”，默认仍使用原视频。普通视频页和 3D Replay
均可为当前 Episode 的八位 4:2:0 HEVC 准备像素无损 H.264 播放副本，准备期间
保留原首帧，可以取消或切回原始播放。没有降低视频分辨率、模型精度、阴影质量
或场景绘制频率，也没有改动原始文件和位姿数据。Intel / D3D11 下兼容副本使用
FFmpegVideoDecoder，避开本机八路 HEVC 硬件解码与 3D 同时工作时的持续卡顿。

固定 64 MB Range 在完整 Episode 上暴露了另一个问题：四路低码率触觉视频的
暂停预加载仍占着 HTTP/1 连接，使高码率腕部的后续请求排队。固定很小的分段
又增加了请求开销，约 40 秒后高码率视频的缓冲余量耗尽。兼容响应现按该相机
约两秒的平均码率分段，限制在 256 KB–32 MB，每次仍只流式读取 64 KB。
原始视频继续使用此前的首段及 2 MB 顺序读取策略。
